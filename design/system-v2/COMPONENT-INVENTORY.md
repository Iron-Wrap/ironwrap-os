the fixed surfaces is generated by "Ask IronWrap" from System v2 components. A generated view may only use a component
listed here as **Generated**, in the states listed as present. This file lists what exists, what each component is
missing, and what the view templates (`TEMPLATES.md`, Track T) still need.

Main findings:

1. **Most of what the reference screens show is not a component.** Builders drew it with the `kit-base.js` helpers, as
   plain frames: about 1,180 `Fact` frames (key-value), about 584 `Panel` frames (section with header and count), about 290
   `Status slot` frames, 676 `Table row` frames, 69 `Compare` rows, about 95 `Action bar (pinned)` frames, plus the
   queue rows, tiles, timelines, calendar and map. A renderer cannot use these. They are the largest part of the gap list.
2. **The AI team parts only have outcome states.** None of the 17 Board 6 components has a hover, focus or pressed
   variant, a loading variant or an "AI unavailable" variant. Each one's description is empty, so its rules live only
   in the board notes. None of them is in the nine-mode proof frame.
3. **Receipt labels are overrides, not properties.** The action labels of AI/Receipt, AI/Receipt row, AI/Alert and
   AI/Proposed value · Field are text overrides on nested Button instances. Any change to a nested Kind or State
   resets them. That is the label read-back risk the LIBRARY-WAVE has to manage.
4. **Board 7 is drawn but not used.** All eight Board 7 components have 0 instances on screens. Toast, Toggle and the
   date picker exist, but no screen uses them yet.

## How this was read

Read-only. No node was changed. The Iron Wrap bridge stopped taking jobs while this ran (the plugin was restarted later),
so the inventory, the instance counts and the mode counts were read through the Figma MCP (`use_figma`) with read-only
scripts. After the restart, a bridge job read the same page from the desktop session and found the same 193 entries:
62 System v2, 110 icons and 21 on the two legacy sheets. A second bridge job checked the counts.

- **Instances** counts only *direct* instances (`getInstancesAsync`, the cloud copy). Instances nested inside other
  instances come on top of these. For example, Button has 4,544 direct and 2,367 nested (6,911 in the desktop session),
  AI/Receipt row has 196 direct and 252 nested (inside AI/Brief section), and Signal chip has 2,021 direct and 902 nested.
  Format: *screens / specimens*, where specimens are the instances on `01 Foundations` and `02 Components`. "Screens"
  includes the UX flow pages.
- **Modes on screens** is the colour and density mode in effect on each direct instance (`resolvedVariableModes`) on
  every page except the two system pages. It shows where a component has been drawn and seen. It does not prove
  contrast. No component sets a mode itself: each one inherits colour and density from its frame. Only five components
  have a drawn nine-mode proof: Button, Field/Text, Checkbox, Toggle and Signal chip, in `Components in every mode`
  (`1000:127789` on `01 Foundations`).
- **States** are checked against eight interaction states: default, hover, pressed, focus, disabled, loading, error and
  selected. Domain states (receipt outcomes, AI unavailable, offline, Not known yet) are added where the contract or the
  coverage matrix asks for them. A state marked "n/a" does not apply to the component, and the reason is given. Hover
  exists only on the office (`TOKENS.md`, Elevation and states).
- No screenshots were taken. This pass reads structure only.

Abbreviations for modes: OL office-light, OD office-dark, FS field-sun, FN field-night, SD shop-dark, SL shop-light,
CL customer-light, CD customer-dark, CS customer-sun. Densities: o office, t touch, g glove. **No instance on any screen
uses shop-light.**

Use: **G** a generated view may use it. **S** shell only: the renderer draws inside the shell and never generates
the shell. **F** fixed surface only. **X** never: design only or superseded.

## Rules every renderer follows

- **Target sizes** come from density (`TOKENS.md`). `target/min` is 24 office, 48 touch and 72 glove. Button sizes:
  Small 24 / 48 / 72, Default 28 / 48 / 72, Large 32 / 64 / 72. Tappable rows are at least `row/min-height`
  (24 / 48 / 72). The renderer sets the frame's density mode; it never resizes a component by hand.
- **Modes:** only the valid pairs (`TOKENS.md`, Where each mode is valid). Office views: OL or OD with office (desktop)
  or touch (phone, tablet). A generated view never picks a field, shop or customer mode unless it renders inside that
  surface.
- **Two signals.** The `You` button kind, the Needs you chip and the You notice appear only when the viewer is the
  person being waited on. Held (red) appears only for held or stopped work. Agent identity and "Proposed" never use
  colour.
- **One primary per context.** A generated view has at most one Primary or You button in view per section. Every action
  is a catalog action, carries its delegation words and leads to a receipt (see gap 1).
- **Text through properties first.** Where a component exposes a text property, set the property. Where it does not
  (marked "layer text" below), the renderer sets the named text layer, and a read-back after rendering must confirm the
  text.
- **Never** use `Legacy/*` parts, the two `Spine/Rail … (design only)` parts or the page-local SALES parts. Never draw
  a hand-built pattern (a `kit-base.js` frame) in a generated view. If a component is missing, the view falls back to
  the closest listed component and the gap goes on the gap list.
- **Unknown is words.** A value nobody has measured is "Not known yet" in its dashed edge, never 0 or a dash. A proposed
  value is never added into a total of facts unless the total also says "Proposed".

## Limits of this pass

- Mode coverage comes from variable modes read on direct instances, not from rendered contrast. Only the five
  nine-mode-proof components were drawn in every mode.
- Instance counts are direct instances in the cloud copy at read time. Builders were active, and the desktop session
  showed about 80 more Buttons. Nested instances are not in the table counts.
- Frame-pattern counts come from a name-prefix scan of the screen pages and are approximate. A frame that a builder
  named differently is not counted.
- "States missing" is judged against the eight-state checklist, the AI-PRIMITIVES outcome table and the coverage
  matrix states (loading, empty, offline, AI unavailable, error, keyboard focus). It does not replace the component gate.
