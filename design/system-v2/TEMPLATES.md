# System v2 generated-view templates

Track T of the Track B design work, under owner decision IRW-R8b (hybrid UI). Fixed surfaces are drawn in Figma
and gated as screens. Everything else is a generated view: Ask IronWrap answers a request with a view spec, and the
renderer draws it from System v2 components using one of six templates. This file is the template contract for
the renderer thread (Track E), the ask API (Track A), the template Figma board and the template gate.

Precedence. The AI team contract (`output/figma-v2/ai-kit/contract.json`, `ironwrap_ai_team_contract_v1`) wins on
actions, delegation and receipt fields. `AI-PRIMITIVES.md` wins on words and AI components. `TOKENS.md` wins on
values. `../ZERO-LEARNING-GATE.md` is the gate. `output/figma-v2/SAMPLE-DATA.md` holds every fact the examples use.
The spec document shape is Track E's `ironwrap_view_spec_v1` (proposal agreed by Track B); where this file needs a
field or a component kind the proposal does not have yet, it is marked **needed** and listed in section 13.

## 1. What a generated view is

A generated view is data, never code. Ask IronWrap (the face, `orchestrator`, watch `owner_requests` or
`role_questions`, action `fact.explain`) answers a request in one of two ways:

- **A plain cited answer** in the conversation (HOME-12), when the answer is one fact or one sentence with sources.
- **A view spec**, when the answer is a set of rows, one record, a comparison, a set of figures, a history or a
  schedule. The conversation shows one line ("Here are the 3 jobs that are stuck") and the link that opens the view
  in the main pane.

Which template answers which request:

| The request asks about | Template | Example |
|---|---|---|
| Several things of one kind, filtered or waiting ("which", "what is waiting", "who has not") | `list` | "Which jobs are stuck?" |
| One named thing: a job, a property, a customer, a supplier, a person, a coil | `record` | "Show me Linda Chu's job" |
| Two to four options for one choice ("A or B", "which is cheaper") | `comparison` | "Westman or Vicwest for Helen Park's panels?" |
| Figures and what they mean ("how are we doing on", "margin", "this month") | `report` | "Are we losing money on any job?" |
| What happened, in order ("history", "what happened", "when did") | `timeline` | "What happened on the Chu job?" |
| Who works where and when ("this week", "crews", "where are") | `schedule` | "Where are the crews this week?" |

Where views open and how they live:

- **Opened from Ask IronWrap.** The view opens in the main pane; the docked conversation closes; the breadcrumb reads
  "Ask IronWrap › {title}" and "Ask IronWrap" reopens the conversation at that answer.
- **Opened from a fixed surface or another view** (Now tile "See the 3 jobs", a "See property record" link): the
  breadcrumb names where the person came from.
- **Saved views.** Navigation destinations that are not fixed surfaces (Sales, Board, Production, Money desk,
  Inventory, People, Work stops, Margin watch) are view specs saved in tenant configuration. A saved spec is not
  regenerated by the AI on each visit; only its read models are fetched again.
- **No AI needed to draw.** Rendering a spec needs only the read models. When the AI service is down, every saved or
  already open view keeps working; only new specs and new proposals stop (section 4.6, AI unavailable).

## 2. The spec document

The document shape is Track E's `ironwrap_view_spec_v1`. The canonical validator and registry live in
`app/src/generated-views/view-spec.ts`; the ask API and the client run the same code.

```json
{
  "schema": "ironwrap_view_spec_v1",
  "spec_id": "vs_…",
  "run_id": "run_…",
  "specialist_id": "orchestrator",
  "catalog_sha256": "sha256:…",
  "template": "list",
  "title": "Jobs that are stuck",
  "data": [
    {
      "id": "stuck",
      "read_model": "owner_now",
      "params": { "section": "cannot_start" },
      "sources": [{ "fact_id": "job/IW-1038", "version": 41, "hash": "sha256:…" }]
    }
  ],
  "slots": {
    "status": [],
    "body": [],
    "side": [],
    "empty": []
  },
  "actions": [],
  "links": []
}
```

Rules this file relies on (Track E's validator rules, plus the template rules of this file):

1. **Known template, named slots.** `template` is one of `list`, `record`, `comparison`, `report`, `timeline`,
   `schedule`. Each template (section 8) declares its slots, the component kinds each slot accepts, and a min and
   max count per slot. A slot not named by the template, a kind the slot does not accept, or a count outside min
   and max is invalid.
2. **Facts only from bindings.** Every value a person reads as a fact (amount, count, time, name, code, state,
   reason) is a binding `{"bind": "<data id>", "path": "<JSON pointer>"}` into a declared data entry, or a row field
   `{"field": "<name>"}` inside a bound collection. Paths must exist in the read model's registry entry.
3. **Literal words are labels.** `title`, labels, headings, count words and empty-hint words are at most 80
   characters, contain no digits, currency signs or URLs, and pass Z2 (section 7). Names of people, jobs and
   places are facts and are always bound.
4. **Catalog actions only.** `actions[].action_id` is an `A1` or `A2` action of the contract, or an `A3` action
   offered as a request ("Prepare … for your approval"), which creates a proposal on Decisions. Never `H`. No
   component approves, declines, accepts, releases, waives or signs. Decisions are reached only through links to
   fixed surfaces (section 5).
5. **No density, theme, colour, icon names, style, HTML or routes.** The shell decides density and theme. The
   renderer decides every colour from the state a read model returns.
6. **Limits.** 64 KB, depth 6, 120 components, 8 data entries, 6 actions, 3 view-level links (Track E). Row links
   inside bound collections do not count against the 3 (they come from read-model fields; section 5.3).
7. **One primary.** At most one component, action or link carries `"primary": true` (**needed** field; section 13).
8. **Invalid spec.** The renderer shows the plain cited answer when the response has one; otherwise "IronWrap
   couldn't show this. Ask another way, or search." with the search entry. Reason codes go to System details and
   to the run (`view_spec_invalid`).

Bindings in examples use parameters that contain record codes (`"job": "IW-1038"`). Parameters are query ids, not
words shown to people, so rule 3 does not apply to them.

A view without a record (the `list`, `report` and `schedule` examples) still draws its title with `record_heading`:
`identity` is `[]` and the view's kind words are its title ("Jobs that are stuck"). The renderer makes it from the
spec's `title` when the `heading` slot is empty (4.1).

Read-model field types decide how a bound value is drawn (registry, Track E): `text`, `money` (minor units and
currency; Geist with tabular figures, every minor digit shown), `count`, `percent`, `measure` (value and unit),
`when` (instant; formatted by place, section 6.5), `person`, `specialist`, `code` (kind label plus code, drawn as
the plain label then the code in `Code text`), `state`, `delegation`, `sources`, `link`, `proposal`, `not_known`
(reason words).

## 4. Renderer behaviour common to every template

Everything in this section is the renderer's. The model never writes it.

### 4.1 The page frame

Top to bottom, desktop: breadcrumb; `title` (or `record_heading`); the **scope line**; the `status` slot; then the
template's own slots; then "Where this came from" (closed disclosure listing every data entry's `sources`).

**Title of a view without a record.** When the `heading` slot is empty, the renderer draws the `title` with
`record_heading`, `identity: []` and the view's kind words as its title: the `Page header` with breadcrumb and no
identity line ("Ask IronWrap › Jobs that are stuck").

**Scope line** (renderer-made from the data entries' fetch times and the provider read-back times the read models
return): "Updated 10:40 · from QuickBooks today 10:31". "Updated" is the latest successful fetch. Each outside
provider that a bound value depends on adds "from {provider} {read time}". At most two providers are named; more
become "from QuickBooks and 2 more" with the list in "Where this came from". The scope line and the status line sit
in one `Status line` strip with the clock glyph, as on every reference frame. A record with `summary_cells` has no
counts sentence: its strip shows the scope line only.

**Section jumps.** When the body holds three or more components with a `heading`, the renderer adds `Section tabs`
under the status line, one per heading. A tab carries a count only when its component holds items a person can act on (`agent_lane` cards,
`list` and `queue` rows): the bound count ("AI team on this job 4"). Tables, timelines, cells and key-value sections
carry none (lead ruling on template board ruling 5).

### 4.2 Ordering

Bound collections keep the read model's order. Every read model that feeds a collection returns it most urgent
first, by one rule: held by a work stop or People only first; then other held items; then items that need the
viewer; then items waiting on someone else; then working; then done; then everything else, newest first. Timelines
are newest first. The renderer never re-sorts except through a filter.

### 4.3 The one primary and the action bar

- At most one control in the view is filled: the primary. It is the `primary` component's first row link, or the
  `primary` link, or the `primary` action. Its fill follows the state of the thing it answers: held → `Button`
  Kind Held; needs you → Kind You; anything else → Kind Primary (ink).
- Every other control is outlined (`Button` Secondary, Small on office rows) or a text link. A row has at most one
  control.
- **Office densities:** the primary is drawn where its row or card is (inside the lead row, card or cell); there
  is no separate bar.
- **Phone density:** the primary and its partner sit in a bottom `Action bar` above the tab bar, never mid-page
  (gate r2c lesson). Primary 64 px, full width; partner 48 px under it; a consequence line above the bar when the
  action has one. The lead row keeps its words but not a second copy of the button.
- **Partner.** The partner is the one other control the bar may hold: for a link to a decision, none; for an
  action, the receipt's "Do it myself" path when the runtime returns one. It names its object ("Write the reply
  myself") (gate r2c lesson).
- **The "Do it myself" line.** Wherever "Do it myself" renders (the partner, a receipt, an AI-unavailable notice), a
  line under the buttons starts with the bold label "Do it myself:" and says what it opens ("Do it myself: opens the
  lead with the call notes filled in; reverts nothing"; AI-PRIMITIVES copy table).
- No primary is valid. Then the status line ends with "Nothing here waits for you" (renderer words, shown only
  when no bound item has `needs_viewer` true).

### 4.4 Layout by density (the shell picks the density; the template picks nothing)

| Shell density | Width | Layout |
|---|---|---|
| Office, comfortable (default) | main pane 1024 px and wider | Body column and a 368 px side column; two-line rows (56 px); receipt cards in two columns when the main pane is 1200 px or wider (a 1440 frame with the sidebar) |
| Office, compact (person's choice, `Segmented control` "Comfortable / Compact" in the filter row; default for a list over 25 rows) | same | One-line rows (32 px); tables at 32 px rows; receipt cards collapse to `AI/Receipt row` (the row opens the receipt sheet); summary cells to one line; side column unchanged |
| Office on phone or tablet (`touch`) | under 1024 px | One column. Order: heading, scope and status, summary, filters (`Segmented control` up to 3 options, else `Field/Select` "Show"), body, then each side component as a section, then "Where this came from". Rows at least 64 px; the whole row is the target and its verb is its last line; tables become stacked cards with labels above values (3 fields, then "See all details"); `Action bar` at the bottom |
| Crew phone (`field-sun` default, `field-night`; `touch`) | 390 px | Only `record` (crew scope), `timeline` and `schedule`; read-only: no `actions`, links only to fixed crew surfaces; no money; Stop work keeps its own fixed slot from the crew shell; all text, secondary text, placeholders and code chips at 7:1 (gate r2c lesson). A crew lead has no office screens in v1: the crew phone scope is the money-hidden view. The scope words go in the status line: "Money is not shown on the crew phone"; a read-only schedule says "Read only: the office changes the schedule" |
| Shop tablet (`glove`) | | No generated views (open question 6) |
| Customer pages | | No generated views; customer pages are fixed |

**Side slot (368 px).** Decision links and queue rows in the side slot draw in their stacked (phone) form, and
`fact_rows` there draw as a `Key-value list`. The side slot never holds the view's primary: a side component with
`primary` (a primary decision link) moves to the body column, after the body's components (8.6).

**Full width.** Three kinds span the body and side columns: the report `table`, the `schedule` grid and the
`agent_lane`. The two columns go on under them.

### 4.5 Density limits (validator checks; section 7 lists them with ids)

Title and labels at most 80 characters. Status line at most 4 counts. Summary at most 5 cells or 4 tiles. Filters
only when a collection has more than 7 rows, at most 4 plus "All". Rows before "Show {n} more": 25 comfortable,
50 compact, 10 phone. Table columns: 7 office, 3 phone fields. Source chips: 3 per fact, then "{n} more sources".
Comparison: 4 options office, 2 side by side on phone (more stack). Timeline: 10 events per page. Schedule: 7 day
columns office, one day per screen on phone. Side slot: 4 components. Charts: 2 per view, each with its table
twin.

### 4.6 States

Each template section lists only its differences from this table.

## 5. Actions, links and delegation

### 5.1 Three kinds of control

| Control | What it does | Receipt | Where it comes from |
|---|---|---|---|
| **Action** | Runs a catalog `A1` or `A2` action, or asks for an `A3` proposal ("Prepare … for your approval") | Always: the runtime returns it and the renderer draws it in place | `actions[]` |
| **Link** | Opens a fixed surface or another view; changes nothing | none | `links[]` (view level, max 3) and row links from read-model fields |
| **View command** | Filter, show more, compact or comfortable, try again, check again ("Check {source} again", for a provider such as QuickBooks or a supplier such as Vicwest), ask again, hide until tomorrow | none; reads only | the renderer |

### 5.2 How each delegation appears in a generated view

The renderer derives the words from the contract and the current setting; the spec never states them. The chip
shows the state of that action for that thing in that place (gate r2c lesson): "Paused here" after a person took
over the conversation, "Asks first" while the auditor holds the specialist, never the general setting when the
thing in view is in another state. Order of derivation: `human_only` → People only; `protective` → Always on:
protects you; specialist paused → Paused; this item taken over or silenced → Paused here; specialist held by the AI
auditor, launch rule or proof-first rule (contract delegation rules 7 and 10) → Asks first (Always asks first when
`delegable` is false); otherwise the setting.

| Words (chip, `AI/Delegation`) | Contract | Before the step, in a view | Control in the view | After the step |
|---|---|---|---|---|
| Reads and watches | `A0` | A line in a side component ("AI auditor reads and watches: checks every hour; last 10:31, next 11:31") | none | A check row: Done for you, "Can't be undone: it only checked. Nothing changed, so there is nothing to undo." (one check, not a standing watch) |
| Prepares | `A1` | Its output is Proposed (`proposed_value`, `fact_rows` proposal, `agent_lane` proposal block), never a fact | An action may start one ("Draft gutter work into a new quote"); the draft itself has no button | Receipt Done for you (drafted); the decision on it is a link |
| Acts within your limits | `A2`, `within_limits`, effect inside IronWrap | Nothing before; it runs | An action may start one (`followup.pause` "Pause the follow-up") | Receipt Done for you; Undo lives on the receipt (link "See receipt for {object}") with its own line "You can undo this until {time}"; a standing watch has "Stop {the watch}" in place of Undo (5.3). A step above the ceiling asks first: Needs you, "Above your limit of {limit}: it asks you" |
| Asks first | `A3`, delegable | Needs you (blue) when the viewer may decide; "Waiting on {name}" in ink otherwise | A link to the decision ("Review purchase order"); or, when no proposal exists yet, an action "Prepare … for your approval" that creates one on Decisions | Working on it ("Waiting for QuickBooks to confirm"), then Done for you with "Approved by {name}" in Checked |
| Always asks first | `A3`, `delegable` false | As Asks first | As Asks first; no delegation control anywhere in a generated view | As Asks first |
| People only | `H` | Needs you for a person who may do it, and the names of who may ("Only you or Tom Lachance can release it") | A link to the decision ("Review the work stop"); never an action | Done by {name} |
| Always on: protects you | `protective` | Shown after it acted: Held receipt or Done for you ("Payments held since 08:14 by AI bookkeeper") | none on the protection; lifting it is its own People only or Always asks first decision, reached by a link | — |
| Off until you turn it on | `off_until_enabled` | Listed only in a "What it may do" side component; nothing runs | link "See in Settings › AI team" (owner only, surface `settings_ai_team`, **needed**) | — |
| Practice only | `shadow` (the owner's setting, never a start state) | Nothing is sent or changed; the person does the real work as before | none in a generated view (the setting lives in Settings › AI team) | A "Practice run" receipt beside what the person did, never under Done for you or in Decisions; a hold or a pause stops practice runs and keeps the setting |
| Paused / Paused here | setting / state | Nothing new starts; items already waiting stay | none | — |

**Launch rule.** At launch every action with an outside effect asks first. The renderer refuses a spec that offers
an action whose contract `side_effect_class` is `money`, `legal`, `safety`, `external_irreversible` or
`external_reversible` as anything but a request "Prepare … for your approval", and it never draws a Done for you
for such a step before a person approved it.

### 5.3 Links to decisions

- A decision link opens the fixed surface: `decision` with the decision id (the HOME-05 decision detail family,
  including the approval sheet, the passkey step and the work-stop release), `decisions` (the list), `receipt`
  with a step id (the AI/Receipt surface, titled "What the AI did", with Do it myself and, on Done for you only,
  Undo), `now`, `job_record` (until the job record is generated everywhere).
- Labels of decision links come from the decision read model and always start with "Review" ("Review the work
  stop", "Review reply", "Review purchase order", "Review payment match", "Review crew and date", "Review the
  renewal", "Review the pitch"). A link never uses the decision's own verb ("Approve", "Apply", "Release"),
  because the decision happens on the fixed surface (gate r1b lesson: a label must not promise what the click does
  not do).
- Receipt links read "See receipt for {object}", the object being the step ("See receipt for filling the lead",
  "See receipt for sending the deposit invoice"); the receipt opens with the title "What the AI did". This link has this one
  name everywhere (ZL-8). Approval links read "See what {she, he, they} saw"; their accessible name carries the
  object ("See what Dana Whitford saw for the deposit invoice").
- On the receipt (AI-PRIMITIVES copy table): Undo appears only on Done for you, with its own line ("You can undo
  this until {time}" or "Can't be undone: {reason}"); never on Needs you, Working on it or Held. A standing watch's
  Done for you receipt has "Stop {the watch}" ("Stop the storm watch") in place of Undo, with the line "Stopping
  ends {what it does}. You can ask IronWrap to start it again."; never "Can't be undone" for a watch. "Do it myself"
  has its "Do it myself:" line (4.3).
- Row links come from read-model fields (`decision_link`, `receipt_link`, `record_link`, or `next_link`: the
  decision link when the row needs the viewer, else the record link), so a list of 25 rows can link 25 decisions
  without passing the 3 view-level links.

### 5.4 Actions

- `label` is literal (no digits), verb plus object, never "Open", "Go", "Submit", "OK". An `A3` request reads
  "Prepare {object} for your approval". A label that names a person is a binding to the words the read model
  returns for that action ("Send the task to Tom Lachance", 8.4), because names are facts (section 2, rule 3).
- `target` is a binding to the id the action acts on. A row action binds with `*` and is drawn on each row.
- The consequence line comes from the runtime's action words for that action, never from the spec: "Creates a
  proposal on Decisions. Nothing leaves IronWrap." for every `A3` request.
- Every press returns a receipt; the renderer draws it in place of the button (4.6, After an action).

## 6. Provenance and signals

### 6.1 Every fact cites a source

- Every bound fact is drawn with its `AI/Source chip` from the read model's `sources` field: glyph by kind (Record,
  Document, Message, Photo, Reading), plain label, code in mono after it, time ("QuickBooks check today 10:31",
  "Measurement report p. 3", "Stop report Yesterday 09:12").
- A source the read model marks unreadable is not drawn as a chip; its words go in the provenance line ("page 4 of
  the report was unreadable"), as the r1 verdict asked for the pitch.
- A fact read by an AI specialist from a document and not checked by a person carries the provenance line "Read by
  {AI specialist} from {source} · Not checked by a person yet" (r2 verdict fix 9).
- The data entry's `sources` (what the specialist read when it built the view) are listed in "Where this came from"
  at the end of the view.

### 6.2 Proposed is not fact

- AI output nobody accepted is `AI/Proposed value`: the word "Proposed", the open diamond, the dotted edge, and the
  line "Proposed by {AI specialist} from {source}". A proposal can show who it waits for ("waits for Priya Nand").
- No component accepts or changes a proposal in place. The decision is a link (5.3).

### 6.3 Totals

The renderer computes totals; read models may also return totals with the same rules.
- A total adds only facts. A proposed value is never added; if a read model returns a total that includes one, the
  total carries "Proposed".
- If any value in the column is Not known yet, the total is Not known yet with the reason "{n} not known yet", or,
  when the read model marks it partial, the known part with the words "so far · the total is not complete yet"
  (JOB-14 "Cost posted so far").
- Money totals keep currency and every minor digit. Amounts in different currencies are never added.

### 6.4 Signals

- Only two colours carry meaning. Red (`signal.held`) for held or stopped; blue (`signal.you`) for items waiting on
  the viewer. Everything else is ink with a glyph and words.
- Blue only when the read model says `needs_viewer` true. The same item for someone else is ink: "Waiting on Dana
  Whitford". "Waiting on {name}" (ink) is a state of the `agent_lane` card (`AI/Receipt`) and of the `AI/Receipt row`.
- Money receipts (a payment match) and money events are hidden from a viewer without money rights; the timeline
  then says "Showing the {n} newest events you may see".
- Red only for `state` held: a work stop, held payments, a held receipt, a quarantined coil. "Cannot start" for a
  material shortage or a missing crew is ink (SAMPLE-DATA: red is the safety stop on IW-1038 only).
- No colour-only meaning: every signal has its glyph and its words (`Signal chip` kinds Needs you, Held, Done,
  Waiting, Not known yet, Proposed, Working on it). A held or waiting row is never dimmed.

### 6.5 Words, codes and times

- One word per thing: names come from the read model, and a thing has one name in a view. Literal labels that refer
  to it use that thing's word, never a synonym ("outreach plan" and "proposal" for one item failed r2c).
- Codes appear only after their plain label: "Job IW-1038", "Quote V4", "Coil PMS-2231"; only the code is mono.
- Times come as instants and the renderer formats them with the day: office "Today 10:31", "Yesterday 15:12",
  "Mon 16:05"; crew phone and customer "7:12 a.m.". Within the last 6 days a weekday name; older, the tenant's short
  date format. The brief keeps "Brief made 6:50 a.m.".
- Money is Geist with tabular figures ("CAD 12,600.00"), as on every reference frame (open question 1).

## 8. Templates

Each template: purpose and three requests; slots with accepted kinds and min/max; layout per density; renderer
states that differ from 4.6; actions and links; provenance and signal notes; a complete example spec with the
canonical sample facts; what the renderer draws for it.

### 8.1 `list` (list or queue)

**Purpose.** Several things of one kind that share a condition, most urgent first, each with why it is in the list
and its one next step. Answers "which", "what is waiting", "who has not", "what is held".

Requests: "Which jobs are stuck?" · "What is waiting for me on money?" · "Which leads have not heard from us in a
week?"

**Slots**

| Slot | Accepts | Min | Max | Notes |
|---|---|---|---|---|
| `heading` | `record_heading` | 0 | 1 | Only when the list belongs to one thing ("Open decisions on Linda Chu's job") |
| `status` | `status_line` | 1 | 1 | First count in the request's word |
| `summary` | `macro_tile` | 0 | 4 | Only for queues with money or counts worth a glance (Money desk) |
| `filters` | `filter_bar` | 0 | 1 | Only when the collection can exceed 7 rows |
| `body` | `list`, `decision_links`, `receipt_rows`, `table` | 1 | 2 | One main collection; an optional second ("Found", "Done for you") |
| `side` | `key_values`, `text`, `alert`, `source_chips` | 0 | 3 | What the list means; who does what |
| `empty` | `empty_hint` | 1 | 1 | |

**Layout.** Comfortable: body column with two-line `List row`s (title; meta with the code after its label and the
reason; state chip and delegation chip right; proposal on a third line as `AI/Proposed value` Inline; the row link
at the end). A `list` with `heading: null` draws its Panel without a header. Compact: one-line rows, the proposal folds behind the row. Phone: 64 px rows, state under the title,
the link verb as the last line, the primary in the `Action bar`. Crew phone: not allowed (the crew's lists are the
fixed Today and crew items screens).

**States (differences).** Empty: the status line's zero words as the title. A row whose read model sub-part fails
keeps its title, says "Couldn't read this row just now." and offers "Try again".

**Actions and links.** Row links to decisions (5.3). Row actions only for `A1`/`A2` or `A3` requests. The primary
is the first row's link when `primary` is set on the main collection.

### 8.2 `record` (record detail)

The most used view. People open job and property records more than anything else, so this template has the
richest slots and the most states. Record kinds: job, property and roof, customer, supplier, person, coil, quote.
The job record and the property and roof record are the reference examples (JOB-14 and HOME-11 frames).

**Purpose.** Everything about one thing on one page: where it stands, what the AI team did and needs, what is known
and what is not, its history, its money, who approved what.

Requests: "Show me Linda Chu's job" · "What do we know about the roof at 1180 Tamarack Bend?" · "Is the Harlow job on
track, and is anything costing us?"

**Slots**

| Slot | Accepts | Min | Max | Notes |
|---|---|---|---|---|
| `heading` | `record_heading` | 1 | 1 | Name (address for job and property), identity line ("Job IW-1038 · Linda Chu · Job record") |
| `status` | `status_line` | 0 | 1 | Used when the record has no summary cells (property: proposed and not-checked counts) |
| `summary` | `summary_cells`, `macro_tile` | 0 | 4 | One `summary_cells` (up to 5 cells: state, held, needs you, money, unknown), or up to 4 `macro_tile` |
| `alerts` | `alert` | 0 | 2 | Risks and opportunities about this record; above the body |
| `body` | `agent_lane`, `fact_rows`, `timeline`, `table`, `proposed_value`, `key_values`, `text` | 1 | 6 | Order: `agent_lane`, `fact_rows`, `timeline`, `table`; each with a `heading` (section jumps); `text` only as a closing line under a table |
| `side` | `approvals`, `decision_links`, `key_values`, `list`, `fact_rows` | 0 | 4 | Who approved this; contact; related records; warranty |
| `empty` | `empty_hint` | 1 | 1 | For a record with no facts, events or receipts yet |

**Section rules**

- `summary_cells` answers "on track, stuck on what, is it costing us" with no click (T1 passed with 0 actions on
  JOB-14). Cell states: plain, held (red tint, the held sentence), needs you (blue: "{n} decisions need you." and
  their names), money, not known (Not known yet with its reason). A held cell says who may release it.
- `agent_lane` ("AI team on this job"): one `AI/Receipt` per open or recent step, from the receipts read model,
  ordered by 4.2 (what needs the viewer before working items); the proposals the receipts made sit after all the
  cards, each an `AI/Proposed value` Block with a line naming the receipt it came from ("Contact rule: call Linda
  Chu before every crew visit" · "From AI customer care's reply to Linda Chu"). In a generated view the receipt's
  decision is a link ("Review the work stop", "Review reply", "Review payment match"), never an approve button;
  "See receipt for {object}" opens the fixed receipt ("What the AI did") with Do it myself and, on Done for you
  only, Undo (5.3). With `primary`, the first card's decision link is the view's primary.
- `fact_rows` ("The roof"): label; value; provenance line (read by whom, checked by a person or not); source chips;
  a proposal drawn as `AI/Proposed value` Field without Accept and Change, with the reason and the decision link
  ("Review the pitch").
- `timeline`: people and AI specialists mixed, newest first, each AI item with "See receipt for {object}"; 10 then
  "Show older events".
- `table` ("Money on this job"): label, what it is, amount, source chip; Not known yet rows keep their place; the
  profit row is Not known yet with its reason until the job is finished and every cost is in; a closing line
  "Nothing proposed is added to these figures."
- `approvals` ("Who approved this"): each approval with who, when, what they saw, and "See what {she} saw".
- Crew items to confirm (JOB-14 IW-1031 state): when the job has them, the timeline read model returns them first
  under their own heading, each as a row with its decision link ("Review the check-in"), until answered.

**Layout.** Comfortable: heading; scope; summary strip of cells across the body width; section tabs; `agent_lane`
across the body and side columns (4.4) as cards in two columns when the main pane is 1200 px or wider (a 1440 frame
with the sidebar), one column below; `fact_rows` and `timeline` in the body column; side column with approvals,
related record links, contact (stacked rows, 4.4). Compact: summary cells one line each; the lane becomes
`AI/Receipt row`s (each opens its receipt sheet); timeline one line per event. Phone: cells stacked; the lane as
`AI/Receipt row · Phone` with the decision verb as the row's last line (LIBRARY-WAVE 4; r2 verdict fix 2: the rows
keep the desktop card titles); side components after the body; the primary in the `Action bar`. Crew phone (crew
scope): heading, summary cells without money, timeline, links to the crew's fixed job screens; no `agent_lane`
decisions, no `table` of money.

**States (most complete)**

| State | Record behaviour |
|---|---|
| Loading | Heading and identity at once (from the request's entity); 5 cell skeletons; per section 3 skeleton cards or rows at final height; the side column's skeletons; section tabs without counts until rows arrive |
| Empty record | A new record with no events, facts or receipts: the heading draws; each empty section collapses to one line ("No AI team steps on this job yet"); the `empty_hint` gives the one next step ("Nothing has happened on this job yet. Add it to the Production plan." as a link) |
| Partial / unknown | Cells, fact rows and money rows show Not known yet with the reason ("Cost of the stop: crew idle time is not tracked and the deck repair is not priced yet. It is known once the deck repair is priced and the crew's idle hours are entered.") |
| Proposed facts | Drawn as proposals, never in totals; the status line counts them ("1 roof fact is proposed") |
| Read by AI, not checked | Value plus "Read by AI measurer from page 3 of the report · Not checked by a person yet"; counted in the status line |
| One section fails | That section draws its `Notice` with "Try again"; summary and other sections draw (a QuickBooks outage never blanks the timeline) |
| Held (work stop open) | The held summary cell and the lane's People only card first; the primary is "Review the work stop" (Held fill) |
| After a decision on a fixed surface | On return the record re-fetches: the cell becomes "Work stop released." with who and when ("Released by Dana Whitford … Today 14:40, with her passkey"), the decision leaves the lane, the timeline gains the events (JOB-14 work-stop-released frame) |
| AI unavailable | Facts, money and timeline draw from read models; the lane's waiting receipts show Held "its AI service is not answering" and "Do it myself" with its "Do it myself:" line on the receipt (no Undo on Held); no new proposals |
| Stale | Money cells and rows from QuickBooks say "From QuickBooks today 08:10"; the scope line "QuickBooks last read today 08:10: not checked lately" with "Check QuickBooks again" |
| Offline | Saved copy, "Saved 10:40. You are offline."; decision links stay visible but open the decision in read-only with "Approvals wait until you are back online" |
| No access | A role without money rights sees "Only Accounting and the owner see money on this job." in place of the money table and the money cell |
| Not found | "This job is not in your records." with "Search work" |
| Merged or duplicate record | When the read model returns a proposed merge (K. Harlow into Kara Harlow), it is a proposal with its decision link; the record never merges in place |

**Actions and links.** Record decisions are links (lane, fact rows, side decision links). Record actions are `A1`
or `A2` of the record's specialists (for example `quote.draft_revision` "Draft gutter work into a new quote",
`customer_message.draft` "Draft an update to the customer") or `A3` requests. View-level links: the related record
("See property record", surface `view`, **needed**) and "See all decisions".

### 8.3 `comparison`

**Purpose.** Two to four options for one choice, side by side on the same criteria, with the difference worked out
and the AI's proposed option marked Proposed. Answers "A or B", "which is cheaper", "what changed between V3 and V4".

Requests: "Westman or Vicwest for Helen Park's panels?" · "What changed between quote V3 and quote V4 for Kara
Harlow?" · "Compare the two crews for Kyle Brandt's job."

**Slots**

| Slot | Accepts | Min | Max | Notes |
|---|---|---|---|---|
| `heading` | `record_heading` | 1 | 1 | The thing the choice is for ("Purchase order for Helen Park's job") |
| `status` | `status_line` | 1 | 1 | Options compared, proposed, needs you |
| `body` | `comparison_columns`, `proposed_value`, `table`, `receipt_rows`, `decision_links` | 1 | 4 | `comparison_columns` first |
| `side` | `key_values`, `text`, `source_chips` | 0 | 3 | What the choice is for: needed by, on hand, the job's state |
| `empty` | `empty_hint` | 1 | 1 | Fewer than two options |

**Rules.** Criteria rows in the request's order of importance; money criteria before time; the `versus` criterion
draws the difference against the proposed option under every other option's value, as "{difference} more" or
"{difference} less" ("CAD 109.60 more" under Vicwest's landed cost), computed by the renderer from bound money, same
currency only; the criterion's label gives the context. The proposed option carries `AI/Proposed value` "Proposed" in its
result row, never a colour. An option with a Not known yet value in the `versus` criterion gets no difference line
and the status line says "1 option not known yet".

**Layout.** Comfortable: options as columns (max 4), criteria as rows, the `versus` row strong. Compact: same, 32 px
rows. Phone: two options side by side; three or four stack as cards with the same criteria order; the `Action bar`
holds the primary. Crew phone: not allowed.

**States (differences).** Empty (fewer than two options): "Only one quote is in: Westman Steel." with the one next
step from `empty_hint`. Stale supplier quote: its column says "Quote from Mon: not checked lately".

**Actions and links.** The decision is a link (`decision_links` or a row link) to the proposal on Decisions. When
no proposal exists yet, an `A3` request may be offered ("Prepare the Westman Steel order for your approval",
`purchase_order.place`), which creates the AI buyer's proposal on Decisions.

### 8.4 `report` (report or analysis)

**Purpose.** Figures about many things at once and what they mean: the answer sentence first, a few tiles, then
the rows behind them, with what is not known said plainly. Answers "how are we doing on", "are we losing money",
"this month".

Requests: "Are we losing money on any job?" · "How much is waiting for my approval on money?" · "How did the AI
team spend its budget this month?"

**Slots**

| Slot | Accepts | Min | Max | Notes |
|---|---|---|---|---|
| `heading` | `record_heading` | 0 | 1 | When the report is about one thing (a specialist's month) |
| `status` | `status_line` | 1 | 1 | The answer: zero words carry the reassuring case ("No job is below zero margin") |
| `summary` | `macro_tile` | 0 | 4 | Known or Not known yet; each tile names its source |
| `alerts` | `alert` | 0 | 3 | Risks and opportunities the figures produced |
| `body` | `table`, `chart`, `proposed_value`, `receipt_rows` | 1 | 5 | At least one `table`; every `chart` has its table twin |
| `side` | `key_values`, `text`, `source_chips` | 0 | 3 | How a figure is worked out, with the numbers bound |
| `empty` | `empty_hint` | 1 | 1 | |

**Rules.** Charts label every point with its exact value; a Not known yet point is a gap with its words, never zero;
a proposed series is dashed and named "Proposed"; no chart without the table that holds the same numbers. A
report's totals follow 6.3. A report normally has no primary; a decision found by the report is a row link.

**Layout.** Comfortable: answer strip, 4 tiles across, alerts, table full width, side "How it is worked out".
Compact: tiles to one line each, 32 px rows. Phone: tiles two per row; table as stacked cards; chart full width
above its table twin. Crew phone: not allowed (reports carry money).

**States (differences).** Partial: the status line adds the unknown count ("4 jobs: not known yet"). Stale: tiles
from a stale provider say so in their source line.

**Actions and links.** Usually none. A follow-up for a person, such as the AI auditor's proposal to find the cause of

it names a person (5.4). The auditor's own escalations show as receipts, never as buttons. While the AI is not
answering the action is not offered (4.6).

### 8.5 `timeline`

**Purpose.** What happened to one thing, in order, people and AI specialists mixed, each step with its source or
receipt. Answers "what happened", "who did what", "when did".

Requests: "What happened on the Chu job?" · "Who touched Paul Moreau's deposit invoice?" · "What did the AI team do
this morning?"

**Slots**

| Slot | Accepts | Min | Max | Notes |
|---|---|---|---|---|
| `heading` | `record_heading` | 0 | 1 | The thing the history is about |
| `status` | `status_line` | 1 | 1 | Events, by the AI team, by people |
| `filters` | `filter_bar` | 0 | 1 | Everyone (All), People, AI team; money; safety |
| `body` | `timeline` | 1 | 1 | |
| `side` | `decision_links`, `key_values`, `receipt_rows` | 0 | 2 | What still waits on this thing |
| `empty` | `empty_hint` | 1 | 1 | |

**Rules.** Newest first; every time carries its day; people as `Avatar/Person`, AI specialists as `AI/Badge` with
"AI …" in the name, customers as people; AI items link "See receipt for {object}"; an approval item links "See
what {she} saw". The one-clock rule: no Today event later than the scope line's "Updated" time. Crew items to confirm
stay on top under their own heading until answered (JOB-14 IW-1031 frame). Filters never hide held or waiting items
without saying so ("2 held items hidden by this filter"); a work stop counts as a held item ("1 held item is hidden
by this filter: Sam Keewatin stopped the work."). Money events (and money receipts) are hidden from a viewer without
money rights, and the page says "Showing the {n} newest events you may see" (6.4).

**Layout.** Comfortable: time column (96 px), actor, what happened with its detail line, link at the end. Compact:
one line per event. Phone: time above the actor line; the link as the last line; 64 px rows. Crew phone: the crew's own job
only ("What happened on this job"), read-only, no money events, AI items without a receipt link (receipts are
office surfaces), `field-sun` by default.

**States (differences).** Empty: "Nothing has happened on this job yet." Loading: 10 skeleton rows. "Show older
events" loads the next page under the last row without moving what is shown.

**Actions and links.** None by default; the side decision links are outlined, no primary (a history is read, not
acted on).

### 8.6 `schedule` (map or schedule)

**Purpose.** Who works where and when: resources (crews, people, the estimator's calendar, trucks) against days,
or jobs on a map, with what cannot start, what is proposed and what is not on the schedule yet. Answers "this
week", "where are the crews", "who is free".

Requests: "Where are the crews this week?" · "When is Priya free for an inspection?" · "Show this week's jobs on a
map."

**Slots**

| Slot | Accepts | Min | Max | Notes |
|---|---|---|---|---|
| `heading` | `record_heading` | 0 | 1 | When the schedule is one resource's ("Sam Keewatin's crew") |
| `status` | `status_line` | 1 | 1 | Booked, proposed, cannot start, not on the schedule yet |
| `filters` | `filter_bar` | 0 | 1 | Resource kinds; needs you; proposed |
| `body` | `schedule`, `list` | 1 | 2 | `schedule` first; `list` for "Not on the schedule yet" |
| `side` | `decision_links`, `key_values`, `alert` | 0 | 3 | Decisions about the schedule; capacity; weather risk |
| `empty` | `empty_hint` | 1 | 1 | |

**Rules.** Grid mode: rows are resources, columns are days with the day word ("Wed", "Today" marked in words, not
colour); a block shows start time, the job's name and code, and its state; a proposed block is dotted with
"Proposed" and who proposed it; a held block is red with its reason; past days recolour to `text.tertiary`, never
faded. Map mode (**needed**): one pin per job with the same words as its block, and the list twin always under the
map, so nothing is only on the map. Two blocks for one resource that overlap are drawn side by side, never on top
of each other; the schedule says nothing about a clash unless the read model returns one. A day with nothing for a
resource reads "Not set yet" in ink. A held decision row (the work stop) is red tint with Needs you and its Held
next step.

**Layout.** Comfortable: the grid spans the body and side columns (4.4), up to 7 day columns, resource column
200 px; under it the body column holds the unscheduled list and then the side's decision links when they hold the
primary (4.4); the side column holds the rest.
Compact: 32 px blocks with time and code only, the name in the block's accessible name. Phone: one day per screen
with `Section tabs` for the days ("Wed · Thu · Fri · Sat"), blocks as rows. Crew phone: only the crew's own
resource ("My week"), read-only, links to the fixed crew Today and job screens.

**States (differences).** Empty: "Nothing is on the schedule this week." Stale weather or delivery checks: the
block keeps its line "Weather checked Today 06:45". Offline: "Who is working now is not known while you are
offline."

**Actions and links.** Decisions about crews and dates are links. A job with no start date may offer the `A3`
request `crew_date.commit` "Prepare a start date for your approval" (the AI scheduler drafts it with
`schedule.draft` and the proposal appears on Decisions). `crew_slot.hold` (A2, Acts within your limits) runs by
itself and shows only after the fact.
